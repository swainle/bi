# 平台分套：一页看板 = 每个平台各一套内容

> 记录时间：2026-11-12 ｜ 提出人：用户（电商老板，拼多多 + 天猫）
> 这份文档写的是**原始需求**和**落地的技术方案**。以后这段逻辑再出问题，先读这里，
> 再对照 `AGENTS.md §5.1`（硬规则）和代码。
> 相关代码索引见文末「文件清单」。

---

## 1. 原始需求（按用户原话逐条）

1. 看板里有一个「筛选栏」，其中第一个字段是**平台切换器**（「切换数据集」：拼多多 → 一张表，天猫 → 另一张表）。
   有它的时候，这一页要能按平台各放一套内容。
2. 「**切换拼多多平台，这属于拼多多的平台的页面才对**」——切到哪个平台，看到、改的就只是那个平台的内容。
3. 反例（用户 2026-11-12 实测报的 bug）：在「拼多多」平台下删除标题「天猫 • 榜单概况」，
   「天猫」那边也跟着没了 —— 这是错的。**标题、形状也得各平台一份**。
4. 「如指标卡组件可以做到了」——用户拿指标卡当参照：能取数的卡片本来就是分平台的，
   她要求**所有元素**都和指标卡一个待遇。
5. 「网页预览并没生效」（同一天的另一个反馈）——改完不能只在编辑器里对，预览/发布链接必须一致。
6. 补充（同日）：导航菜单卡上的「首视页」决定打开看板先落哪一页，这个开关也必须是「这套内容自己的」。

一句话概括需求：**一页看板 = 平台上的一组内容；平台之间的增删改互不影响，编辑器 / 预览 / 发布三处表现一致。**

---

## 2. 结论：不变量（Invariants）

这四条是这套模型的「宪法」，任何改动都不能破坏：

| # | 不变量 |
| --- | --- |
| I1 | **只有筛选栏是整页共用**（它本身是平台切换器，只能一份）。 |
| I2 | 其余**所有**元素（图表 / 指标卡 / 头标卡 / 导航菜单卡 / 明细表 / 分节标题 / 结论卡 / 词云 / 标题 / 文字 / 形状）都归「当前平台那一套」。 |
| I3 | 任一平台上的新增 / 修改 / 删除，**不得影响其它平台**；跨平台共享同一份数据只允许通过筛选栏参数。 |
| I4 | 编辑器、预览页、发布页读同一份结构、用同一套规则（`view_items_for`），不允许各自维护一套「哪些算共用」的私货。 |

## 3. 数据模型

看板文档 `bi_canvas.doc`（JSON）里，一页是一段：

```jsonc
{
  "views": [
    {
      "key": "main",              // 页面 ID（复制、分享都用它定位）
      "title": "主视图",
      "items":      [ /* 只放筛选栏 */ ],
      "items_map":  { "天猫": [ /* 天猫这一套：卡片 + 标题 + 文字 + 形状 */ ],
                      "拼多多": [ /* 拼多多这一套 */ ] },
      "guides":     [ /* 参考线，整页共用 */ ]
    }
  ]
}
```

- **有平台切换器**：`items` = 筛选栏；其余进 `items_map[平台]`；
- **没有平台切换器**：所有元素都在 `items`，`items_map` 清空（历史残留要清，否则同一张卡会存两份）；
- 一个元素的 ID（`key`）在同一份文档里唯一；**不同平台那套之间允许同 ID**（各自独立的一份），读取时按套取。

后端唯一读入口：

```python
view_items_for(view, platform) = 「筛选栏（来自 items）」 + 「items_map[platform]」
```

- 平台没配 → 只剩筛选栏；
- 没选平台 → 先拿第一套顶着（避免整页空白）。

## 4. 技术方案（分四层）

### 4.1 编辑器（`frontend/src/pages/CanvasBoardPage.tsx`）

| 环节 | 做法 |
| --- | --- |
| 分类 | `isViewLevelItem(item)` **只认筛选栏**（`isFilterBarItem`）。这是唯一分类函数，前后端必须同口径 |
| 落回文档 | `stashView()`：切页 / 切平台 / 保存前调用 —— 筛选栏 → `items`，其余 → `items_map[activePlatform]`；没平台切换器时全部回 `items` 并清 `items_map` |
| 切平台 | `platformRef` 记录当前平台；切换时先把旧的落回 doc，再装目标平台那套；**目标平台第一次进入就复制当前这套当起点**（含标题/形状），所以不会白板 |
| 旧结构迁移 | `migratePlatformSplit(doc)`：载入时若发现 `items_map` 存在、但标题/形状还挂在 `items` 上 —— 把它们**按原 key 复制进每个还没有标题/形状的平台那套**，然后 `items` 只留筛选栏。内存里就迁好，不用等保存 |
| 选中态 | 切平台后只保留「新那套里还存在」的选中元素 |

### 4.2 后端（`backend/app/dashboards/models.py`）

| 环节 | 做法 |
| --- | --- |
| 共用判定 | `_shared_filter_items(view)` **只返回筛选栏**（历史文档里 `type` 存成 `chart` 的筛选栏用 `component` 兜底识别） |
| 渲染 | `view_items_for(view, platform)`：共用（筛选栏）+ 该平台那套；平台那套里若混进筛选栏会剔除 |
| 旧结构过渡 | `view_items_for` 对「页面级还挂着标题/形状」的旧文档**先照常渲染**（算作共用），避免「还没保存就先少一截」；下一次保存即被 heal 迁走 |
| 保存自愈 | `heal_view_filters(view)`：① 页面级 `items` 残留的非筛选元素复制进每个**还没有**标题/形状的平台那套；② 平台套里的筛选栏收回到页面级一份；③ 同套内同 key 去重。无 `items_map` 时原样返回 |
| 现场版面渲染 | `_with_live_items()`：编辑器把「现场 items」发给 `/render` 时**清掉 `items_map`**，否则库里那份会和现场卡片叠在一起 |
| 按 key 找元素 | 一律用 `doc.all_items()`（同时遍历 `items` 与所有平台套），不要只遍历 `view.items` |

### 4.3 预览 / 发布页（`frontend/src/pages/DashboardPage.tsx`）

- 合并口径与后端一致：`shared = items.filter(type === "filter")`，再拼 `items_map[platform]`；
- 平台从渲染响应里拿（`render.platform`），筛选值来自地址栏 `p_*` 参数；
  ⚠️ 2026-11-12 修过：预览页原先把 URL 里的 `p_*` 直接丢掉（`readParamQuery` 写了没人调用 +
  换看板时 `setParams({})` 又抹一次），所以「预览带平台」一直是假生效。

### 4.4 与其它功能的交叉点

| 功能 | 交叉规则 |
| --- | --- |
| 前端 ID 展示 | 页面 ID = `views[].key`；元素 ID = 元素 `key`。同 ID 可能出现在两个平台那套里，定位要带平台 |
| 导航菜单卡「首视页」 | 开关挂在菜单项 `nav.items[].active`；查找函数 `navHomePage(doc)` 同时扫 `items` 和所有 `items_map` 套 |
| 导航菜单卡「跳转页全展示」 | 编辑器只读影格 / 预览注入都按 `spec.nav.global_nav` 判定，同样两处都扫 |
| 组件数据源账本 | `bi_dash_item_source` 按 `dashboard_id → view_key → item_key → dataset_id` 记录；筛选栏按平台映射的绑定，`role` 记成 `platform:天猫` / `platform:拼多多` |
| 页面级元素（标题/文字/形状） | **不再共用**。旧文档由迁移/heal 分到各平台，同 key 各一份 |

## 6. 回归验收清单（改动这段逻辑后逐条跑）

1. 建看板：筛选栏（平台切换器：拼多多 / 天猫）+ 12 个元素
   （柱状 + 指标卡 + 头标卡 + 导航菜单卡 + 明细表 + 分节标题 + 结论卡 + 词云 + 标题 + 文字 + 形状 + 筛选栏）。
2. 打开编辑器，默认平台下 **12 个都在**。
3. 「平台」下拉切到另一个平台：**12 个也都在**（各一份副本，可独立编辑文字）。
4. 在平台 A 删除任意元素、改任意标题，保存 → 查库：
   `items` **只有筛选栏**；平台 B 那套**数量与内容不变**。
5. 预览 / 发布链接 `?view=main&p_platform=平台B`：平台选中 B，渲染的是 B 那套；
   `p_platform=平台A`：A 那套（两边标题/卡片不同）。
6. 旧文档（标题/形状还挂在 `items`）：打开展示不缺内容；保存一次后结构变成「每平台一份」。
7. 无平台切换器的看板：所有元素照旧在 `items`，`items_map` 为空，行为不变。
8. `bash scripts/ui_rules.sh`（内含 `tsc --noEmit`）通过；后端重启后 `/api/health` 200。

## 7. 分套判定改版（2026-11-12 晚，用户需求）

> 原方案把「分套」固定绑在「平台」上：筛选字段配了 `dataset_map` 才分套。
> 用户指出：分类名不一定叫「平台」（也可能是品类 / 榜单…），要一个更灵活的入口 ——
> **在筛选字段的「名称」下方加「分套依据」开关**。

**新语义**：字段显式勾选「分套依据」（`FilterFieldSpec.split = true`）即成为分套依据。

| 项 | 规则 |
| --- | --- |
| 判定 | `isSplitField(field) = field.split === true \|\| dataset_map 非空`（后者兼容历史看板） |
| 取值（`items_map` 的 key） | 有 `dataset_map` → 用它的键；否则用字段的 `options[].v` |
| 唯一性 | 同一筛选栏只能有一个分套依据；勾选新的会自动清掉其它字段的 `split` 与 `dataset_map`。**多开（平台×品类这种组合键）2026-11-12 用户确认暂不做**，先保持单开 |
| 数据集切换 | `dataset_map` 仍可配（每个取值绑一张表）；不配也能只按取值分套 |
| 前端判定点 | `frontend/src/features/components/split.ts` → `CanvasBoardPage`（`activePlatform` / `hasPlatformSwitcher` / `boundPlatforms`）、`FilterBar`（`isDatasetSwitch` / `optionsOf`） |
| 后端判定点 | `app/dashboards/render.py::_is_split` → `_switcher_value` / `resolved_fields` / `_platform_value`；`app/components/spec.py::FilterFieldSpec.split` |
| 不变式 | I1–I4 全部不变（筛选栏共用、其余按套、互不影响、三处同口径） |

编辑器入口：选中筛选栏 → 中栏筛选字段卡片 →「名称」输入框下方的「分套依据」开关。

回归补充：构造看板「筛选栏字段 = 品类（甲类 / 乙类，只勾 split、不绑数据集）」，
`items` = 筛选栏、`items_map = {甲类: […], 乙类: […]}` → 预览默认显示甲类那套（实测通过）。
