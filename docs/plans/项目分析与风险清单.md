## 1. 产品定位与能力面

面向电商团队（榜单端 / 需求端·天猫 / 拼多多）的自研 BI 底座，代替外部 BI 工具，独立仓库 / 数据库 / 部署。

已落地能力（按板块）：

- **数据接入**：15 类数据源（PG / MySQL 家族 / ClickHouse / Doris / StarRocks / SQL Server / Oracle / Db2 / Presto / Hive / Impala / Redshift + CSV·Excel），类型清单一源 `sources/types_catalog.py`，驱动可用性实时探测；结构快照、漂移检查、单表重同步、定时自动同步、后台导入任务（202 受理 + 轮询）。
- **语义层**：数据集 / 字段 / 指标，公式字段、指标认证与版本、口径变更快照、字段级血缘、dbt/LookML 导入（plan → apply 两段式）。
- **查询层**：`QueryObject` 契约、多方言编译（`builder.quote`）、时间粒度、语句超时、每用户并发配额、慢查询落库、查询取消、直连源库。
- **分析画布**：自由坐标 + 8px 吸附、撤销重做、图层树、按页保存（`PUT …/views/{key}`）、页面增删改、平台分套（`items_map`）。
- **看板 / 组件**：23 种 kind（见 §3.3）、页面参数链路、图表联动 `cross_filters`、下钻明细、浮层动作、收藏视图。
- **交付与运营**：指标告警、定时报表（HTML/Excel/PDF/PNG）、站内/Webhook/钉钉/企微/邮件通知、模板库与团队协同、整页导出。
- **企业能力**：RBAC + 数据范围（all / dept_and_children / dept / self）、注册审批、操作审计、数据集行列权限、错误日志、Sentry/GlitchTip。
- **AI / Agent**：NL→SQL、一键生成看板、三阶段 Agent 管线；MCP 网关（工具授权、冻结、每日额度、幂等、草稿乐观锁、审计）。

## 3. 架构与核心契约

### 3.1 请求链路（看板渲染）

```
浏览器 → Vite(:9201 dev) / Nginx(prod)
      → FastAPI(:9202)
         SecurityWatch → CSRF → RateLimit → Logging → AuditUser
         → dashboards/router.py  _can_read/_can_edit
         → dashboards/render.py  render_dashboard（每卡独立 Session + 线程池）
         → components/spec.validate_spec → resolver → semantic/compiler
         → query/builder（方言）→ security/sql_guard → rls 注入 → masking
         → query/executor（超时/配额/慢查询/取消）
      ← payload（卡片数据 + 生成的 SQL + elapsed_ms）
```

渲染结果有 15s 短时缓存（`render_cache.py`），key 含用户 / `updated_at` / 视图 / 参数 / 现场版面。

### 3.2 看板文档模型（`bi_canvas.doc`，v2.1）

- `header.stats[]`：头标卡统计；`views[].items[]`：共用元素（筛选栏）；
- 平台分套：`views[].items_map = {平台: [元素…]}`，后端只认 `view_items_for(view, platform)`；
- 元素类型：`chart`（组件实例，自带 spec）· `filter` · `heading` · `text` · `divider`；
- 保存路径：整份文档 `PUT /bi/dashboards/{id}`（支持 `expected_updated_at` 乐观锁）、单页 `PUT …/views/{key}`（`FOR UPDATE` 锁行）。

### 3.3 组件 spec

`KINDS` 23 种（`components/spec.py:17-28`），按角色分：

| 角色 | kind |
| --- | --- |
| data（18） | kpi table bar hbar line area pie donut scatter heatmap wordcloud combo rank_list funnel gauge radar waterfall map |
| content（3） | insight banner nav |
| structure（1） | section |
| param（1） | filter |

前端 `registry.tsx` 的 `KIND_LABEL` 与后端一致（23 个）。组件库现有 23 个启用行（`bi_component where archived=false`）。

### 3.4 安全链

`security/sql_guard/`（sqlglot AST，单语句只读）→ `security/rls/`（编译/注入/指纹，fail-closed）→ `security/masking.py`、`dataset_rules.py`（行级 AND、列级数据集优先）→ `security/nav_guard.py`（业务入口写操作）。鉴权按请求现算，不信 JWT 快照。

### 3.5 权限模型

`roles = 功能权限 + data_scope`；权限码白名单 `admin/permissions.py::VISIBLE_PERMISSION_CODES`（7 个后台分区 + 5 个业务入口 + 3 个 AI 能力）；`users` 三拆分（`account_type` / `position` / `department_id`）+ 注册审批（pending 挡在登录前）。

## 6. 风险清单

### R1 · 同页并发编辑静默覆盖（P1 · 用户决定暂缓）

- **现象**：两人同时编辑同一页，后保存者覆盖先保存者，无提示、无冲突记录。
- **证据**：`dashboards/repository.py:101` 的 `save()` 支持 `expected_updated_at` 乐观锁，但前端全仓库无一处发送该字段、页面也无 409 处理；`repository.py:125` 的 `save_view()` 只做到「不同页互不覆盖」（`FOR UPDATE` 锁行后只替换该页）。
- **影响**：违反 `docs/开发规范.md:257`「写操作幂等或带乐观锁；禁止 last-write-wins 覆盖他人编辑」；多人同时编辑是协同看板的既定用法。
- **建议（未执行）**：前端在保存时带上进入页面时的 `updated_at`，后端 409 并返回最新文档摘要，前端弹「此页已被他人修改」二选一（覆盖 / 放弃）。

### R2 · 最新保存链路没有回归测试（P1）

- **证据**：`backend/tests` 无任何文件引用 `save_view` 或 `/views/`；`CanvasBoardPage.tsx` 的 `dirty` / `docDirty` 状态机无单测。11-23 一天内为「未保存」连打三个补丁（CHANGELOG 顶部三条）。
- **影响**：这块逻辑靠实测迭代，任何后续改动都可能静默回退，且回退不会被 CI 拦住。
- **建议（未执行）**：后端补 `save_view` 的正常/不存在/并发/字段校验四类用例；前端把 `dirty` 推导抽成纯函数并有单测。

### R3 · 自定门禁失效且未接入 CI（P2）

- **证据**：`check_file_limit.py` 实跑失败；`pyflakes` 不在 `pyproject.toml` 依赖里；`ci.yml` 只有后端 pytest / 前端 typecheck·单测·build·storybook·budget / 镜像冒烟，**不含**文件行数、pyflakes、E2E、视觉回归、`perf`。
- **影响**：`docs/开发规范.md` §6 列出的 11 项门禁里，至少 4 项形同虚设；规范与实际执行脱节会持续放大。
- **建议（未执行）**：把 `check_file_limit` 与 pyflakes 装进 CI（单 job）；E2E/视觉保持本地门禁但在 PR 模板里要求贴结果。

### R5 · 单文件行数红线普遍突破（P2）

- **影响**：说明「改完就跑，不跑 typecheck」的做法曾真实发生；结合 R3，建议把 typecheck 作为提交前强制项。
